# 小米 R3G + ImmortalWrt 24.10.6 校园网路由器实践

本文记录一套以小米 R3G 为硬件、ImmortalWrt 24.10.6 为系统的路由器配置流程。目标是让 R3G 通过校园 Wi-Fi 上联，并为 LAN 内设备提供统一的网络出口。

本文只记录当前方案：R3G、ImmortalWrt 24.10.6、Linux 6.x、UA3F 发布版 IPK、ShellCrash 和 RuijieEportal 认证脚本。历史设备、历史固件和已经弃用的加密编译流程不再作为操作步骤。

## 0. 方案概览

~~~text
LAN 设备
   |
小米 R3G / br-lan
   |  Wi-Fi STA 上联
校园 Wi-Fi / 锐捷 ePortal
   |
互联网
~~~

R3G 的无线接口作为 STA/客户端连接校园 Wi-Fi，LAN 侧设备继续连接 R3G 的有线或无线网络。认证脚本在 R3G 上访问外部探测地址，触发校园网的 ePortal 拦截页面，再提交账号和加密密码。

认证成功后，校园网侧看到的是 R3G 的上联设备。LAN 内设备通过 R3G NAT 共享这个上联出口。

### 0.1 本文版本基线

| 项目 | 配置 |
| --- | --- |
| 硬件 | 小米 R3G |
| SoC 平台 | MediaTek MT7621 |
| 固件 | ImmortalWrt 24.10.6 |
| 内核 | Linux 6.x |
| 上联方式 | 校园 Wi-Fi 2.4 GHz 或 5 GHz STA |
| 认证脚本 | 本仓库 src/rjeportal.sh |
| MIPS 加密程序 | dist/encrypt_mipsel_24kc |
| 示例 LAN 地址 | 192.168.5.1 |

无线接口名、LAN 网段、校园网网关和认证门户地址都可能因环境不同而变化。本文命令里的 IP、SSID、账号和密码必须替换为现场值。

## 1. 准备工作和风险边界

### 1.1 需要准备的硬件和文件

- 小米 R3G 路由器；
- 一台带 RJ45 网口的电脑；
- 一根网线；
- ImmortalWrt 24.10.6 对应 R3G/MT7621 的固件或源码；
- 校园 Wi-Fi 的 SSID、Wi-Fi 密码和网页认证账号；
- Breed 文件 breed-mt7621-xiaomi-r3g.bin；
- 用于保存备份文件的电脑磁盘。

建议首次操作时只连接电脑、R3G 和电源，先完成 SSH、备份和刷机，再把设备接入正式校园网络。

### 1.2 设备识别和网络策略说明

校园网可能根据上联设备的 MAC、IP、TTL、IPID、HTTP 特征或连接行为识别设备。本文的当前方案使用 UA3F 处理 UA 特征，并使用 ShellCrash/Clash 提供反 DPI 的代理链路；两者需要配合使用。这个方案来自实际校园网环境的测试，不保证适用于所有学校，也不应绕过学校明确禁止的网络管理策略。

下面的视频用于理解校园网设备识别和路由器上联的整体思路，不是 R3G 刷机教程：

- [面对校园网的多设备检测，「我」的解决方案是](https://www.bilibili.com/video/BV1Tm4y1H7dy/)

## 2. 小米 R3G 获取 SSH、备份和刷入 Breed

刷机顺序建议固定为：

~~~text
官方/开发版系统
      |
      v
获取 SSH
      |
      v
备份所有 MTD 分区、factory/EEPROM 校准数据和当前固件
      |
      v
刷入 Breed
      |
      v
通过 Breed 刷 ImmortalWrt 24.10.6
~~~

不要在没有备份的情况下直接刷写 bootloader、factory 或 EEPROM 相关分区。

### 2.1 获取开发版系统和 SSH 权限

R3G 的官方系统、开发版和设备支持信息可以从 [MiWiFi 下载页](https://www.miwifi.com/miwifi_download.html) 开始查找。通常需要先刷入适合当前硬件版本的开发版，再按照对应教程开启 SSH。

如果设备是特殊运营商版本，获取 SSH 的流程可能与普通零售版本不同。下面的资料用于说明设备绑定和开启 SSH 的背景流程，实际以当前设备版本和页面提示为准：

- [小米 WiFi/路由器绑定流程](https://cdn.cnbj1.fds.api.mi-img.com/ics-resources/articles/60559916ec317cb4ee2cf1f9.html)：用于了解小米 WiFi 账号与设备绑定。
- [米家 App 绑定路由器流程](https://cdn.cnbj1.fds.api.mi-img.com/ics-resources/articles/5fec3cf11019330eae6c2753.html)：部分特殊版本需要先完成米家绑定。
- [小米路由器 R3G 刷机教程](https://post.smzdm.com/p/a6plozqe/)：用于对照开发版、SSH 和后续刷机顺序。
- [小米路由器 3G 刷 Breed/OpenWrt 的记录](https://blog.csdn.net/michaelchain/article/details/124263191)：用于补充 R3G 特有的刷机注意事项。
- [小米路由器 R3G 刷 Breed/OpenWrt 教程](https://www.bilibili.com/read/cv26996006/)：用于对照实际操作画面。

获取 SSH 后，先通过网线登录当前系统。地址可能是 192.168.31.1 或设备当前 LAN 地址：

~~~shell
ssh root@192.168.31.1
~~~

如果 SSH 服务尚未启动，先在官方/开发版系统中确认 SSH 权限已经生效，再继续备份。不要为了追求一步完成而跳过备份。

### 2.2 记录设备信息和 MTD 分区

进入 SSH 后先记录硬件、系统、网络和 MTD 分区信息：

~~~shell
uname -a
cat /proc/cpuinfo
cat /proc/mtd
ip addr
ip route
~~~

把这些输出保存到电脑。尤其要保存 /proc/mtd，因为后续备份和刷 Breed 要根据实际分区名称确认目标，不能直接套用其他教程中的 mtd0、u-boot 或 Bootloader。

### 2.3 备份当前固件、EEPROM 和 factory 数据

R3G 的无线校准、MAC 等信息通常位于名为 factory 的 MTD 分区中，某些系统也可能使用 EEPROM、eeprom、ART、calibration 或其他名称。不同固件的分区编号不能假设相同。

先查看分区：

~~~shell
cat /proc/mtd
grep -iE 'factory|eeprom|art|calib|u-boot|bootloader|firmware' /proc/mtd
~~~

创建备份目录并读取所有 MTD block 设备：

~~~shell
mkdir -p /tmp/r3g-backup
cat /proc/mtd > /tmp/r3g-backup/proc-mtd.txt

for dev in /dev/mtdblock*; do
    [ -e "$dev" ] || continue
    name=$(basename "$dev")
    dd if="$dev" of="/tmp/r3g-backup/$name.bin" bs=64K
done

sha256sum /tmp/r3g-backup/* > /tmp/r3g-backup/SHA256SUMS
ls -lh /tmp/r3g-backup
~~~

至少应保存：

- bootloader/Breed 之前的 bootloader 分区；
- bootloader 环境分区；
- factory 或等价的 EEPROM/校准/MAC 分区；
- 当前 firmware 分区；
- /proc/mtd 输出；
- SHA256 校验文件。

如果系统没有 /dev/mtdblock*，先检查是否提供 nanddump 或其他 MTD 读取工具。目标是保存设备的原始分区内容，不是只备份 LuCI 配置。

把备份复制到电脑，不能只留在路由器的 /tmp 中：

~~~shell
scp -r root@192.168.31.1:/tmp/r3g-backup .
~~~

在电脑上再次计算并核对 SHA256。备份中可能包含设备校准数据、MAC 信息或其他敏感信息，不要上传到公开仓库。

### 2.4 下载并校验 Breed

Breed 是独立的引导管理器，不是 ImmortalWrt 固件。它可以用于备份分区、选择启动分区和刷写后续固件。

R3G 对应的文件通常是：

- [breed-mt7621-xiaomi-r3g.bin](https://breed.hackpascal.net/breed-mt7621-xiaomi-r3g.bin)
- [Breed 官方文件索引](https://breed.hackpascal.net/)

在电脑上下载后先计算校验值：

~~~shell
sha256sum breed-mt7621-xiaomi-r3g.bin
~~~

再上传到路由器临时目录：

~~~shell
scp breed-mt7621-xiaomi-r3g.bin root@192.168.31.1:/tmp/
~~~

### 2.5 刷入 Breed

刷写前再次确认 bootloader 分区名称：

~~~shell
cat /proc/mtd
grep -iE 'u-boot|bootloader' /proc/mtd
~~~

如果输出中确实存在名为 Bootloader 的分区，常见写法是：

~~~shell
mtd -r write /tmp/breed-mt7621-xiaomi-r3g.bin Bootloader
~~~

Bootloader 只是常见分区标签。若 /proc/mtd 显示其他名称，必须使用实际标签；不要把其他设备教程中的分区名直接套用。

刷写期间不要断电、不要拔网线，也不要关闭 SSH 会话。设备重启后，按照 Breed 对 R3G 的进入方式访问 Breed Web 管理页。常见做法是断电、按住复位键上电并保持一段时间，但不同硬件批次可能有差异，以 Breed 页面和设备指示灯状态为准。

进入 Breed 后，第一件事仍然是使用 Breed 的备份功能再次保存 bootloader、factory/EEPROM 和完整闪存。Breed 页面显示的分区名称和大小应与 SSH 阶段保存的 /proc/mtd 记录相互对照。

## 3. 编译 ImmortalWrt 24.10.6 固件

如果已经有确认适配 R3G 的 ImmortalWrt 24.10.6 固件，可以直接跳到第 4 节。只有需要自定义软件包、内核功能或首次验证构建流程时，才需要自行编译。

### 3.1 为什么选择 ImmortalWrt 24.10.6

本文使用 ImmortalWrt 24.10.6 作为固定版本基线：

- 项目对 MT7621/R3G 目标有现成支持；
- 24.10.6 使用 Linux 6.x 内核系列；
- 固件、软件包和本文后续配置保持同一版本；
- 需要自定义内核模块或 LuCI 软件包时，可以从同一源码树构建。

发布说明和源码入口：

- [ImmortalWrt v24.10.6](https://github.com/immortalwrt/immortalwrt/releases/tag/v24.10.6)：确认版本和发布说明。
- [ImmortalWrt 项目仓库](https://github.com/immortalwrt/immortalwrt)：查看 Target、Subtarget 和设备 Profile。
- [ImmortalWrt Firmware Selector](https://firmware-selector.immortalwrt.org/)：选择设备固件并核对目标平台。

### 3.2 为什么使用 WSL2

如果主机是 Windows，推荐用 WSL2 Ubuntu 编译。ImmortalWrt 构建依赖大量 Linux 工具，直接在 Windows Shell 中构建容易遇到路径、权限、符号链接和大小写问题。

下面的资料用于解决 WSL 环境差异：

- [OpenWrt 在 WSL 中构建的官方说明](https://openwrt.org/docs/guide-developer/toolchain/wsl)：重点关注文件系统、依赖和构建限制。
- [Windows 11 安装 WSL2 Ubuntu 参考教程](https://blog.csdn.net/weixin_44301630/article/details/122390018)：用于完成 Ubuntu 子系统安装。

源码和构建目录建议放在 WSL 的 Linux 文件系统中，例如 ~/projects/，不要放在 /mnt/c/ 下。

### 3.4 拉取源码和 feeds

以下命令固定使用 v24.10.6 标签，避免主分支变化导致不同构建结果：

~~~shell
mkdir -p ~/projects
cd ~/projects

git clone --branch v24.10.6 --single-branch --filter=blob:none \
  https://github.com/immortalwrt/immortalwrt.git
cd immortalwrt

./scripts/feeds update -a
./scripts/feeds install -a
~~~

如果需要 IPID 相关内核模块，可以加入 rkp-ipid。它和 UA3F 是独立组件，是否需要取决于校园网的识别策略：

~~~shell
git clone https://github.com/CHN-beta/rkp-ipid.git package/rkp-ipid
./scripts/feeds update -a
./scripts/feeds install -a
~~~

### 3.5 配置 Target、LuCI 和内核功能

启动配置界面：

~~~shell
make menuconfig
~~~

R3G 的目标应选择 MT7621 对应的 ramips/mt7621，Profile 选择小米 R3G 或对应 MT7621 设备 Profile。不要直接复制其他设备的 .config，应在配置界面确认 Target、Subtarget 和 Profile。

按需选择：

- luci-app-ttyd：通过浏览器使用终端；
- luci-app-argon-config：LuCI 主题配置；
- luci-app-fileassistant：文件管理；
- ipset；
- iptables-nft 及当前版本可用的兼容模块；
- kmod-rkp-ipid：仅在确认需要时选择。

软件包名称会随版本和 feeds 变化。若某个包在 24.10.6 中不存在，先搜索当前 feeds：

~~~shell
make menuconfig
./scripts/feeds search PACKAGE_NAME
~~~

如果需要调整 Netfilter 内核选项，可进入：

~~~shell
make kernel_menuconfig
~~~

实践中使用过的相关选项主要位于：

~~~text
Networking support
  -> Networking options
    -> Network packet filtering framework (Netfilter)
      -> Core Netfilter Configuration
~~~

按实际模块依赖选择：

- Netfilter NFNETLINK interface；
- Netfilter LOG over NFNETLINK interface；
- Connection tracking support；
- Connection tracking netlink interface；
- NFQUEUE and NFLOG integration with Connection Tracking。

### 3.6 WSL 环境变量和编译

WSL 中如果主机环境变量混入 Windows 路径，可能导致工具链选择错误。编译前可以使用干净的 PATH：

~~~shell
export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
echo "$PATH"
~~~

通常不需要手动修改 vermagic。只有在明确需要与某个已发布内核模块匹配时，才参考：

- [ImmortalWrt Firmware Selector](https://firmware-selector.immortalwrt.org/)

完成配置后开始编译：

~~~shell
make download -j$(nproc) V=sc
make -j$(nproc) V=sc
~~~

构建成功后，R3G/MT7621 的固件通常位于：

~~~text
bin/targets/ramips/mt7621/
~~~

刷写前核对文件类型、目标设备、版本和 SHA256。保留最终使用的 .config，方便量产时复现。

## 4. 通过 Breed 刷入 ImmortalWrt 24.10.6

### 4.1 选择正确的固件

在 Breed Web 页面刷写时，选择适用于 R3G/MT7621 当前分区布局的固件。文件名中的 target、subtarget 和 device profile 必须指向 R3G/MT7621。

刷写前再次确认：

- 当前仍可以进入 Breed；
- SSH 阶段和 Breed 阶段的备份都已经下载到电脑；
- 固件版本为 ImmortalWrt 24.10.6；
- 文件不是其他 MT7621 设备的固件；
- 不会勾选清除 Breed 或覆盖 bootloader 的选项。

上传固件后先核对文件大小和校验值，再执行刷写。刷写完成后等待设备自动重启，不要中途断电。

### 4.2 首次进入系统

通过有线 LAN 连接设备，登录新系统。默认地址取决于固件和此前 LAN 配置，常见是 192.168.1.1：

~~~shell
ssh root@192.168.1.1
~~~

进入后检查：

~~~shell
cat /etc/openwrt_release
uname -a
ip addr
ip route
~~~

确认：

- 发行版版本为 ImmortalWrt 24.10.6；
- 内核为 Linux 6.x；
- Target 为 ramips/mt7621；
- LAN 地址和 DHCP 服务符合预期；
- Breed 仍可按需要进入。

## 5. OpenWrt 基础配置

### 5.1 配置 LAN 和校园 Wi-Fi 上联

推荐第一次配置使用 LuCI：

1. 先通过网线进入路由器；
2. 在无线页面扫描校园 Wi-Fi；
3. 分别确认校园 Wi-Fi 的 2.4 GHz 和 5 GHz SSID；
4. 新建或修改一个 STA/客户端接口；
5. 将 STA 接口加入 WAN 或单独的上联网络；
6. 确认路由器获得校园网侧 IP；
7. 确认默认路由经过 STA 接口。

命令行检查：

~~~shell
ip addr
ip route
iwinfo
~~~

正常情况下应该能看到 STA 接口、校园网侧 IPv4 地址和对应默认路由。无线接口名不在本文中固定，因为不同驱动和配置可能使用不同名称。

### 5.2 安装常用 LuCI 软件包

~~~shell
opkg update
opkg install \
  luci-app-ttyd \
  luci-app-argon-config \
  luci-i18n-argon-config-zh-cn \
  luci-i18n-ttyd-zh-cn \
  luci-app-fileassistant
~~~

如果需要通过 LuCI 管理启动和维护脚本，可以安装 nettask：

~~~shell
cd /tmp
wget https://gh-proxy.com/https://github.com/lucikap/luci-app-nettask/blob/main/luci-app-nettask_2.0.0-1_all.ipk \
  -O luci-app-nettask.ipk
opkg install luci-app-nettask.ipk
~~~

IPK 必须与当前系统架构、LuCI 和依赖版本匹配。安装失败时保留错误输出，不要直接忽略依赖。

## 6. 安装 UA3F 和 ShellCrash

### 6.0 为什么两者都要安装

这里要区分“认证脚本的代码依赖”和“整套路由器方案的网络依赖”：

- `rjeportal.sh` 只负责触发 ePortal、获取认证参数和提交账号密码，它本身不会调用 ShellCrash；
- UA3F 用于处理校园网可能识别的 HTTP User-Agent 特征；
- ShellCrash 运行 Clash/Meta，为 UA3F 提供当前校园网测试中需要的反 DPI 代理链路。

实践中曾尝试只使用 UA 特征处理方案。设备开始时可以正常联网，但运行一天后被校园网抽样封禁，表现为加入黑名单并在上线后被封禁约 10 分钟。后来改为 UA3F 配合 ShellCrash/Clash 的反 DPI 配置，才形成当前稳定方案。因此，本文的实际部署中 ShellCrash 不是“想代理时才安装”的可选工具，而是与 UA3F 配套的必要组件。

因此当前实践统一使用 UA3F + ShellCrash/Clash 组合，不再混用互相冲突的特征处理和代理方案。

### 6.1 安装 UA3F 发布版 IPK

当前方案直接使用 UA3F 发布的 IPK，并通过 LuCI 兼容包提供管理支持。

先安装依赖：

~~~shell
opkg update
opkg install \
  luci-compat \
  ipset \
  iptables \
  iptables-mod-tproxy \
  iptables-mod-extra \
  iptables-mod-nat-extra \
  kmod-ipt-conntrack \
  iptables-mod-ipopt \
  iptables-mod-nfqueue \
  iptables-mod-conntrack-extra \
  kmod-nf-conntrack-netlink \
  kmod-nft-queue \
  kmod-nft-tproxy
~~~

确认 R3G 当前架构：

~~~shell
grep DISTRIB_ARCH /etc/openwrt_release
~~~

R3G 常见目标为 mipsel_24kc。下载匹配的 UA3F IPK：

~~~shell
cd /tmp
wget https://gh-proxy.com/https://github.com/SunBK201/UA3F/releases/download/v1.9.1/ua3f_1.9.1-r1_mipsel_24kc.ipk \
  -O ua3f_mipsel_24kc.ipk
opkg install ua3f_mipsel_24kc.ipk
service ua3f reload
~~~

如果发布版本或文件名变化，应以 [UA3F Releases](https://github.com/SunBK201/UA3F/releases) 为准，不要安装不匹配的 IPK。

相关资料：

- [UA3F GitHub 仓库](https://github.com/SunBK201/UA3F)：查看安装方式、版本和兼容架构。
- [UA3F jsDelivr 目录](https://cdn.jsdelivr.net/gh/SunBK201/UA3F@master/)：GitHub 下载不稳定时查看资源路径。

如果安装脚本或资源下载出现 Connection reset prematurely，先检查资源 URL 是否仍然存在，再考虑使用 jsDelivr 镜像。不要把旧 URL 和新版本文件混用。

### 6.2 安装和配置 ShellCrash

ShellCrash 是当前校园网方案的必要组件。它不是 `rjeportal.sh` 的代码依赖，但需要在认证前启动并加载 Clash/Meta 配置，用于处理反 DPI 流量。

~~~shell
opkg install curl wget iptables nftables crontab net-tools ubus iproute-doc

export url='https://testingcf.jsdelivr.net/gh/juewuy/ShellCrash@master'
wget -q --no-check-certificate -O /tmp/install.sh "$url/install.sh"
sh /tmp/install.sh
. /etc/profile
~~~

进入配置界面：

~~~shell
crash
~~~

实践使用过的配置思路：

- 运行模式选择 Redir；
- “只代理常用”根据实际网络需求选择；
- 导入 ua3f-socks5-cn.yaml 或其他当前可用配置；
- 按 ShellCrash 版本选择 Meta 内核和本地面板；
- 面板地址和 SOCKS5 端口以 ShellCrash 当前配置为准。

R3G 的 MT7621 性能有限，运行 Clash/Meta 时更适合使用国内代理或规则较精简的配置。全局代理、复杂规则集和过多订阅会明显增加 CPU、内存和延迟；如果需要更复杂的代理策略，应考虑性能更高的路由器平台。

资料：

- [ShellClash 加密防检测教程](https://sunbk201public.notion.site/ShellClash-d199f43309e44ab4b4d4ece01dbac3bb)

## 7. 防火墙、IPID 和时间配置

本节保留实践中使用过的规则，但它们不是 RuijieEportal 认证脚本的必要依赖。ImmortalWrt 24.10.6 默认使用 firewall4/nftables，直接追加 iptables 规则可能与现有规则冲突。先在单台设备上验证，量产时再决定是否启用。

### 7.1 安装相关组件

~~~shell
opkg update
opkg install \
  kmod-rkp-ipid \
  iptables-mod-conntrack-extra \
  iptables-mod-filter \
  kmod-ipt-ipopt \
  iptables-mod-ipopt \
  iptables-mod-u32 \
  iptables-nft \
  ipset
~~~

如果某个包在 24.10.6 中不存在，应以当前 feeds 为准，不要从旧系统复制内核模块。

### 7.2 自定义启动规则

下面示例使用 192.168.5.1 作为 LAN 侧路由器地址。如果 LAN 地址不同，请替换 DNAT 目标：

~~~shell
# DNS 重定向到本机
iptables -t nat -A PREROUTING -p udp --dport 53 -j REDIRECT --to-ports 53
iptables -t nat -A PREROUTING -p tcp --dport 53 -j REDIRECT --to-ports 53

# 防 IPID 检测
iptables -t mangle -N IPID_MOD
iptables -t mangle -A FORWARD -j IPID_MOD
iptables -t mangle -A OUTPUT -j IPID_MOD
iptables -t mangle -A IPID_MOD -d 0.0.0.0/8 -j RETURN
iptables -t mangle -A IPID_MOD -d 127.0.0.0/8 -j RETURN
# 如果校园内网使用 10.0.0.0/8，结合实际情况决定是否保留下一条
# iptables -t mangle -A IPID_MOD -d 10.0.0.0/8 -j RETURN
iptables -t mangle -A IPID_MOD -d 172.16.0.0/12 -j RETURN
iptables -t mangle -A IPID_MOD -d 192.168.0.0/16 -j RETURN
iptables -t mangle -A IPID_MOD -d 255.0.0.0/8 -j RETURN
iptables -t mangle -A IPID_MOD -j MARK --set-xmark 0x10/0x10

# 防时钟偏移检测
iptables -t nat -N ntp_force_local
iptables -t nat -I PREROUTING -p udp --dport 123 -j ntp_force_local
iptables -t nat -A ntp_force_local -d 0.0.0.0/8 -j RETURN
iptables -t nat -A ntp_force_local -d 127.0.0.0/8 -j RETURN
iptables -t nat -A ntp_force_local -d 192.168.0.0/16 -j RETURN
iptables -t nat -A ntp_force_local -s 192.168.0.0/16 -j DNAT --to-destination 192.168.5.1

# 通过 iptables 修改 TTL
iptables -t mangle -A POSTROUTING -j TTL --ttl-set 64

# 拒绝 AC 的 Flash 检测请求
iptables -I FORWARD -p tcp --sport 80 --tcp-flags ACK ACK \
  -m string --algobm --string ' src="http://1.1.1.' -j DROP
~~~

建议在启动前检查规则是否已经存在，避免重复执行时不断追加相同规则：

~~~shell
iptables-save
fw4 print
logread | tail -50
~~~

### 7.3 NTP 配置

系统时间不正确会影响 HTTPS、代理和认证请求。可选 NTP 服务：

~~~text
ntp.aliyun.com

~~~

## 8. 部署校园网认证脚本

本项目的认证脚本位于 [RuijieEportal](https://github.com/Barabama/RuijieEportal)，当前 Shell 入口为 src/rjeportal.sh。

### 8.1 安装 curl

~~~shell
opkg update
opkg install curl libcurl
~~~

认证脚本依赖 curl 完成 ePortal POST 请求。OpenWrt 自带的 uclient-fetch 可能出现：

- pageInfo 返回空内容；
- 登录接口提示“用户名不能为空”；
- 无法可靠处理认证请求。

确认实际工具：

~~~shell
command -v curl
curl --version
~~~

### 8.2 下载项目和检查架构文件

在路由器上执行：

~~~shell
cd /root
wget https://gh-proxy.com/https://github.com/Barabama/RuijieEportal/archive/refs/heads/main.zip \
  -O RuijieEportal.zip
opkg update
opkg install unzip
unzip RuijieEportal.zip
mv RuijieEportal-main RuijieEportal
rm RuijieEportal.zip
chmod +x /root/RuijieEportal/src/rjeportal.sh
~~~

R3G/MT7621 常见目录结构：

~~~text
/root/RuijieEportal/
├── dist/
│   └── encrypt_mipsel_24kc
└── src/
    └── rjeportal.sh
~~~

检查架构和二进制：

~~~shell
grep DISTRIB_ARCH /etc/openwrt_release
ls -l /root/RuijieEportal/dist/encrypt_mipsel_24kc
chmod +x /root/RuijieEportal/dist/encrypt_mipsel_24kc
~~~

脚本会根据 /etc/openwrt_release 的 DISTRIB_ARCH 自动选择加密二进制。自动识别失败时，可以覆盖路径：

~~~shell
export ENCRYPTION=/root/RuijieEportal/dist/encrypt_mipsel_24kc
~~~

### 8.3 测试认证

默认认证门户地址是 172.16.0.46。如果学校使用其他地址：

~~~shell

~~~

先检查状态：

~~~shell

sh rjeportal.sh status
~~~

未认证时登录：

~~~shell
sh rjeportal.sh login YOUR_USERNAME YOUR_PASSWORD
~~~

登录后检查：

~~~shell
sh rjeportal.sh status

~~~

登出：

~~~shell
sh rjeportal.sh logout
~~~

### 8.4 Python 认证方式

## 11. 常见问题

### 11.1 编译环境不稳定

确认源码位于 WSL 的 Linux 文件系统中，而不是 /mnt/c/。清理主机 PATH 后重试：

~~~shell
export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
make clean
make download -j$(nproc) V=sc
make -j$(nproc) V=sc
~~~

### 11.2 R3G 刷机后无法启动

不要继续反复刷写。先：

1. 断电；
2. 确认是否可以进入 Breed；
3. 使用之前保存的 MTD、factory/EEPROM 校准数据恢复；
4. 对照 /proc/mtd 和 Breed 页面分区名称；
5. 再选择与 R3G/MT7621 匹配的固件。

任何恢复操作都必须以实际分区大小和设备备份为依据。

### 11.3 路由器能访问门户，但没有认证参数

认证脚本通过访问外部探测地址触发拦截，不是直接访问 172.16.0.46。确认：

- 上联 STA 已获得校园网侧 IP；
- 默认路由走上联接口；
- 浏览器访问普通外网时确实会跳转认证页；
- PORTAL_IP 指向实际 ePortal 地址。

### 11.4 pageInfo 为空或提示“用户名不能为空”

安装并确认使用 curl：

~~~shell
command -v curl
curl --version
~~~

不要只使用 OpenWrt 自带的 uclient-fetch 运行认证 POST 请求。

### 11.5 加密二进制不可执行

检查架构、文件和权限：

~~~shell
grep DISTRIB_ARCH /etc/openwrt_release
ls -l /root/RuijieEportal/dist/
chmod +x /root/RuijieEportal/dist/encrypt_mipsel_24kc
~~~

R3G 通常使用 mipsel_24kc，对应 encrypt_mipsel_24kc。不要把 mips_24kc、ARM 或 AArch64 二进制放到 MIPS 小端设备上运行。

### 11.6 重启后认证失败

通常是启动顺序问题：STA 尚未关联、默认路由未出现、DNS 未就绪或系统时间不正确。把认证命令放到网络确认之后，并适当增加等待：

~~~shell
sleep 30
ip route
sh /root/RuijieEportal/src/rjeportal.sh status
~~~
